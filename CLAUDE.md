# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Spring Boot 3.5 / Java 17 REST API for tasks (`/api/tasks`), backed by an in-memory H2 database. Built with Maven via the bundled wrapper.

## Commands

```bash
./mvnw spring-boot:run                                   # run on :8080 (H2 console at /h2-console, JDBC URL jdbc:h2:mem:tasks)
./mvnw test                                              # all tests
./mvnw test -Dtest=TaskControllerTest                    # one test class
./mvnw test -Dtest=TaskControllerTest#createRejectsInvalidBody   # one test method
./mvnw package                                           # build jar into target/
```

There is no linter or formatter configured.

## Conventions

- Always build with `./mvnw` on JDK 17, never the system `mvn`.
- Constructor injection only; no field `@Autowired` in `src/main` (test classes use field `@Autowired` for `MockMvc` etc.).
- Request/response DTOs are Java records; never expose entities from controllers.
- All error responses go through `GlobalExceptionHandler` as `ProblemDetail`.
- Every new endpoint needs a controller test (`TaskControllerTest` style) and an integration test (`TaskApiIntegrationTest` style).
- Run the full test suite (`./mvnw test`) after any code change.

## Architecture

Layered, one package per layer under `com.example.tasktracker`:

- `web` — `TaskController` (thin; delegates to the service) and `GlobalExceptionHandler`.
- `service` — `TaskService` owns all transactions (class-level `@Transactional`, `readOnly` on queries) and throws `TaskNotFoundException` for missing IDs.
- `repository` — plain Spring Data `JpaRepository`.
- `model` — `Task` JPA entity; `TaskStatus` enum is persisted as a string.
- `dto` — `TaskRequest` / `TaskResponse` records. Entities never cross the web boundary; map with `TaskResponse.from(task)`. Bean Validation constraints (and their user-facing messages) live on `TaskRequest`.

PUT is a full replace: `update` copies every field from the request, so omitted optional fields become null.

Because of that, the "dueDate not in the past" rule is split: POST enforces it via Bean Validation (`TaskRequest.OnCreate` group, applied with `@Validated` in the controller), while `TaskService.update` rejects a past `dueDate` only when it differs from the stored one (throwing `InvalidTaskException`, mapped to the same 400 shape). This lets clients resend an overdue task's date unchanged, e.g. to mark it DONE.

### Error responses

All errors are RFC 7807 `ProblemDetail` bodies produced by `GlobalExceptionHandler`. 400s always carry an `errors` map (field → message, possibly empty) so clients see one shape whether the failure came from Bean Validation (`MethodArgumentNotValidException`) or from Jackson deserialization (`HttpMessageNotReadableException`). The Jackson handler deliberately classifies the cause (empty body / bad field value / unknown enum value / malformed JSON) and never echoes Jackson's own message, since it leaks internal class names. Tests assert exact `detail` and `errors.*` strings, so changing a message means updating `TaskControllerTest`.

## Tests

Three styles, chosen by what's under test:

- `service/TaskServiceTest` — pure Mockito unit test (`@ExtendWith(MockitoExtension.class)`), repository mocked.
- `web/TaskControllerTest` — `@WebMvcTest` slice with the service as `@MockitoBean`; covers status codes, `Location` header, and the error-body contract.
- `TaskApiIntegrationTest` — full `@SpringBootTest` + MockMvc against real H2. Intentionally **not** `@Transactional` so the service's transaction actually commits; it cleans up with `deleteAll()` in `@AfterEach` instead. Keep it that way.

Schema is generated by Hibernate (`ddl-auto=create-drop`); there are no migrations. `spring.jpa.open-in-view=false`, so lazy loading outside the service's transaction will fail.
